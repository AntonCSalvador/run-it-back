# VCT algorithm and player-tag quick guide

This is the simpler companion to the detailed
[VCT SME review guide](vct-sme-review-guide.md). It explains what the game does
today, what data affects the result, and where a change should be made.

You do not need to be an experienced developer to use this guide. If a change
touches validation, checksums, or generated files, write down the correction and
send it to the repository owner or Codex.

## The algorithm in one minute

The game works like this:

1. Every Champions appearance becomes a separate player card. For example, a
   player's 2022 appearance and 2023 appearance are different cards.
2. The agents played on that card determine its role tags.
3. Match statistics become five hidden ratings: firepower, utility, survival,
   clutch, and consistency. Historical IGL evidence supplies leadership.
4. The player drafts one card for each roster slot: Smokes, Duelist, Initiator,
   Sentinel, and Flex.
5. The five card ratings are averaged. Chemistry and the selected IGL can add a
   bonus.
6. The game builds an opponent in a strength range for the current tournament
   stage.
7. The difference between the two team strengths becomes the chance to win each
   map.
8. A seeded random roll decides each map. Win the BO3 or BO5 to advance.

There are no player-versus-player matchups or map-specific player bonuses right
now. Role tags control who can fill a roster slot. They also affect which
players are compared when ratings are originally generated, but they do not add
a direct role bonus during a match.

## Player cards are tied to an event year

Always identify a player using:

- Player handle
- Team
- Champions year
- Exact card ID

A player can have several historical cards. A statement like “Victor should be
a Duelist” is incomplete because the answer can differ by event year.

The final runtime cards are stored in the yearly files:

- [2021 cards](../src/data/champions/2021.json)
- [2022 cards](../src/data/champions/2022.json)
- [2023 cards](../src/data/champions/2023.json)
- [2024 cards](../src/data/champions/2024.json)
- [2025 cards](../src/data/champions/2025.json)

Use these files to see what the app currently loads. Do not make lasting role or
trait edits directly in them: those fields are generated and can be overwritten.

## How role tags currently work

The role system is based on agents played during that exact Champions event:

- Controller agents count toward Smokes.
- Duelist agents count toward Duelist.
- Initiator agents count toward Initiator.
- Sentinel agents count toward Sentinel.

A role is added when the player used that agent class on at least:

```text
the larger of:
- 2 maps
- 20% of the player's maps
```

If at least two normal roles qualify, the card also gets Flex.

The rule and agent-to-role list are in
[derivation.ts](../src/data/champions/derivation.ts). The calculated counts,
threshold, suggested tags, final tags, and any override are visible in
[evidence.json](../src/data/champions/evidence.json).

### Why crashies and Victor can both show Initiator

For Optic at Champions 2022, the current evidence says:

- `crashies-optic-gaming-2022`: 23 Initiator maps. His tag is Initiator.
- `victor-optic-gaming-2022`: 16 Duelist maps and 7 Initiator maps.
- Victor played 23 maps, so his threshold is 5 maps.
- Seven Initiator maps clear that threshold, so Victor receives Duelist,
  Initiator, and Flex tags.

This does not mean the game believes crashies and Victor had the same primary
role. It means both cards passed the current eligibility rule.

The VCT expert should decide which problem exists:

1. **The agent counts are wrong.** Report which maps or agents are incorrect and
   provide a source.
2. **The counts are right, but the tagging rule is too broad.** Change the global
   rule in [derivation.ts](../src/data/champions/derivation.ts). Possible models
   include primary role only, a higher requirement for secondary roles, or
   separate primary and secondary tags.
3. **This one card is exceptional.** Request a reviewed exception in
   [reviewed-overlays.json](../src/data/champions/reviewed-overlays.json).

Do not “fix” Victor by editing his `eligibleRoles` directly in
[2022.json](../src/data/champions/2022.json). Validation compares it with the
generated result, and regeneration will overwrite it.

## How player ratings currently work

The raw stats are turned into five ratings:

| Rating | What currently influences it |
|---|---|
| Firepower | Average performance rating and ACS |
| Utility | Average assists |
| Survival | Fewer average deaths |
| Clutch | Clutch wins per map |
| Consistency | Less variation in performance rating |
| Leadership | 75 for reviewed historical IGL cards; otherwise 50 |

These are not raw percentages like “this player is 80% accurate.” They are
mostly percentile-style scores comparing the card with players from the same
year and eligible role.

Important current behavior:

- Each map has equal weight.
- Multi-role cards are compared in each eligible role and receive an average of
  those comparisons.
- Missing performance data usually becomes a neutral 50.
- Deeper tournament progression adds a small bonus.
- Maps played do not directly make a card more valuable after its ratings have
  been generated.

The complete calculation is in
[derivation.ts](../src/data/champions/derivation.ts), with a readable explanation
in the [data methodology](data-methodology.md).

### Where to change a player's stats

There is currently no simple manual “set this player's firepower to 90” balance
file.

For an accurate factual correction:

- Check [raw-extraction.json](../src/data/champions/raw-extraction.json).
- Identify the exact player card, map, and incorrect observation.
- Send the correction and source to the owner or Codex.
- Do not alter pinned raw evidence just to obtain a preferred rating.

For a global algorithm change:

- Edit the formulas, missing-data behavior, comparison groups, or progression
  bonus in [derivation.ts](../src/data/champions/derivation.ts).
- Regenerate with `npm run derive:data`.
- Validate with `npm run validate:data`.

Direct edits to `traits` in a yearly JSON are rejected by validation and
overwritten by regeneration. If frequent hand-balancing is wanted, the project
should first add a dedicated player-balance override file.

## How five players become one team rating

Every card gets a baseline score using these weights:

| Trait | Weight |
|---|---:|
| Firepower | 35% |
| Utility | 20% |
| Survival | 15% |
| Clutch | 15% |
| Consistency | 15% |

The game averages the five card baselines, then adds:

- **Chemistry:** +2 for every pair from the same team and year, capped at +8.
- **Selected IGL:** reviewed historical IGL leadership currently gives +2 when
  that player is selected as the lineup's IGL. An ordinary leadership value of
  50 gives no bonus.

These values live in [rating.ts](../src/features/game/rating.ts).

Changing a player's assigned roster slot does not directly change team strength,
as long as the card is eligible for that slot. However, changing role tags and
regenerating the data can change the player's comparison groups and therefore
their generated ratings.

## How opponents are chosen

The game creates a legal five-role opponent and aims for these team-strength
ranges:

| Stage | Opponent strength |
|---|---:|
| Group | 50–62 |
| Quarterfinal | 58–70 |
| Semifinal | 66–78 |
| Final | 74–90 |

It tries up to 250 seeded candidate lineups and accepts the first one inside the
stage range. If none fits, it uses the candidate closest to the target midpoint.

The ranges are fixed. They do not automatically scale to the user's team.
Changing them in [opponents.ts](../src/features/game/opponents.ts) is the easiest
way to make each stage generally easier or harder.

## How win rates work

For each map, the game compares:

```text
your team strength - opponent team strength
```

Equal teams have a 50% map chance. A stronger team gets a higher chance. The
current curve produces roughly:

| Your strength difference | Map win chance |
|---:|---:|
| -12 | 26.9% |
| 0 | 50.0% |
| +6 | 62.2% |
| +12 | 73.1% |

The chance can never go below 8% or above 92%. That guarantees some possibility
of an upset.

In [rating.ts](../src/features/game/rating.ts):

- Make the curve steeper if stronger teams should win more reliably.
- Make it flatter if results should be more random.
- Lower the 8% floor and raise the 92% ceiling to reduce extreme upsets.
- Keep the lower and upper limits complementary, such as 5% and 95%, if both
  sides should have the same upset protection.

Every map in a series uses the same team-strength chance. Group through
semifinal are BO3; the final is BO5. Longer series favor the stronger team more
often. These series rules live in
[tournament.ts](../src/features/game/tournament.ts).

Map scores are created after the winner is selected. Changing 13–x score ranges
or the 12% overtime chance changes presentation, not who wins.

## Randomness and repeatable results

The game uses seeded randomness:

- Daily mode derives its seed from the UTC date.
- Free Play normally uses a new random UUID.
- Offers, opponents, map names, and results use separate seeded scopes.

With the same seed, choices, lineup, data, and code, the outcome is repeatable.
Changing [rng.ts](../src/features/game/rng.ts) or the scope strings can reshuffle
many results even when the visible ratings remain the same.

## What must be regenerated

Run `npm run derive:data` after an approved change to:

- Role thresholds
- Agent-to-role mapping
- Trait formulas
- Percentile groups
- Progression bonuses
- Reviewed role or IGL overlays

That script updates generated evidence and these card fields: traits, eligible
roles, historical IGL, and card source IDs.

Team/name/identity/card-ID/membership/map-count corrections need coordinated
owner or Codex work because the current generator does not rebuild all of those
fields.

Changes only to [rating.ts](../src/features/game/rating.ts),
[opponents.ts](../src/features/game/opponents.ts),
[tournament.ts](../src/features/game/tournament.ts), or
[draft.ts](../src/features/game/draft.ts) do not require player-data
regeneration.


```text
Current setting:

Should strong teams win more often or should results be more random?

```

## Safe final checks

After an approved local change:

```powershell
npm run derive:data       # only when player derivation or overlays changed
npm run validate:data
npm test
git diff
git diff --check
```

Before committing, confirm:

- The exact player card and year are named.
- Factual corrections have VCT sources.
- Balance preferences are labeled as preferences.
- Generated files changed only because the generator was intentionally run.
- No validation rule or checksum was weakened merely to make the change pass.
- The diff contains no unrelated files.

For deeper technical details, edge cases, and validation ownership, use the
[full VCT SME review guide](vct-sme-review-guide.md).
